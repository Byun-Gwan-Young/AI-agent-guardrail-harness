# 002 세션 시작·종료 API와 재시작 복원

## 배경
S1은 단일 전역 로그를 세션별 파일로 분리했다. 초기 구현은 모든 기존 파일을
409로 거부해 프록시 재시작 후 미종료 대화도 중단시켰다. 이를 수정한다.

## 왜 필요했는지
동일 세션 키만으로 다음 턴과 새 실행의 의도를 구별할 수 없다.
`POST /sessions`는 새 실행의 명시적 시작을 뜻하며, 활성/종료 여부와 무관하게
기존 키를 409로 거부한다. `POST /sessions/end`는 해당 실행의 종료를 뜻하며
파일에 `status: ended`를 저장한다. 두 API 모두 X-Guardrail-Session이 필요하다.
존재하지 않는 세션 종료는 404, 이미 종료된 세션 종료는 멱등적으로 200이다.

## 자동 시작과의 관계
두 API는 선택 사항이다. 프레임워크는 chat 요청만 보내도 자동 시작할 수 있다.
chat 경로는 파일이 없으면 active로 생성하고, active이면 다음 턴으로 이어 쓴다.
재시작 후 active 파일은 턴 기록을 복원하고 경고를 남긴다. ended 파일은 409다.
종료 API를 호출하지 않은 파일은 active로 남는다. finish_reason=stop은 메시지의
끝일 뿐 전체 실행의 종료로 취급하지 않는다. 새 실험에는 새 헤더 키를 사용한다.
헤더가 없는 동일 첫 메시지는 같은 해시이므로 독립 실행을 구분하지 못한다.

## 저장소와 운영 범위
SessionStore는 SessionRepository의 create/load/save에 의존한다. 현재 구현은
JsonSessionRepository이며 create_app(repository=...)로 대체할 수 있다.
파일 status는 active/ended. 기존 S1 closed 불리언은 읽을 때 변환한다.
기존 fixture 배열은 복원 대상으로 인정하지 않고 보존한다.
파일 갱신은 임시 파일과 원자적 교체를 사용한다. 저장 장애는 fail-open이다.
저장이 실패한 최신 턴/종료 상태는 재시작 후 복원되지 않을 수 있다.
현재는 단일 프로세스/worker만 지원한다. Redis 전환 시 async I/O, 세션별 분산 잠금,
원자적 생성·갱신 또는 버전 비교를 추가해야 하며 인터페이스 교체만으로 다중 worker가 보장되지는 않는다.

## 되돌리는 조건
프레임워크 또는 실행기가 명시적인 실행 ID와 신뢰할 수 있는 종료 이벤트를 항상
제공해 두 관리 API의 역할을 대체할 수 있으면 호출자 이전 후 제거한다.
자동 시작은 base_url 변경으로 사용하는 호환 경로이므로 유지한다.
