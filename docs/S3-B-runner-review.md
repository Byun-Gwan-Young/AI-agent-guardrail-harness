# A-1 실행기 구현 및 실행 조건 검토

실행기만 구현했다. A-1 및 외부 API는 실행하지 않았다. 기존 A-1 YAML·자산·criteria_version은 변경하지 않았다. 나머지 10종도 작성하지 않았다.

## 구현

- `experiments/run_scenario.py`: YAML 기반 AutoGen planner/developer/reviewer 순환. **1 step = 한 역할의 on_messages 작업**. 도구 실행 후 응답 정리를 포함해 최대 2 LLM 호출. SDK 재시도는 0이며 프록시의 429 재시도는 별도다. 18 step에서 총 36번의 모델 클라이언트 호출을 넘지 않는다.
- UUID 세션과 새로운 작업 폴더를 만들고 fixture를 복사한다. 원본 suite ID를 사전 확인하며 링크를 거부한다. 파일 도구는 복사본 내부 및 역할별 허용 파일만 수정한다. 원본 해시를 마지막에 재확인한다.
- `GROQ_API_KEY`를 사용하는 모델 요청은 프록시 `/v1`로만 전송한다. 세션·시나리오·실행 번호·실제 프레임워크 버전 헤더를 전달한다. 현재 설치 버전은 AutoGen 0.5.7, OpenAI SDK 3.7.0이다. seed 미검증 상태에서는 seed를 보내지 않는다.
- 매 step 후 별도 인수 검사, 파일 해시 수집, suite ID 재계산. 실패한 검사 실행은 0통과로 위장하지 않고 관측 불가로 기록한다. 기준 버전이 프록시와 다르면 모델 호출 전에 중단한다.
- 프록시 응답의 `X-Guardrail-Turn`을 step에 연결한다. 오류 응답의 턴도 포함한다. 관측 payload를 먼저 저장하고 `/sessions/observations`에 같은 step ID·내용으로 최대 4번 제출한다. 영속 저장 확인까지 실패하면 해당 step을 누락으로 기록하고 중단한다. 409는 재시도하지 않는다.
- 리뷰어의 유효한 completion_declared만 선언으로 인정하고 첫 선언 step을 보존한다. 구조화 출력 오류는 대화값을 null로 남기며 artifact는 수집한다. 기준 경보는 observe_only이며 인수 성공과 선언 또는 max_steps로 종료한다.
- `summary.json`: step 수, 총토큰(null 가능), 확인된 토큰 소계, 최신 기준 판정·경보 이력, 종료 사유, 전후 통과 수, 관측 누락 step 수, 원본 보존 여부. 사람 라벨 actual_outcome은 null이다.
- 원본 fixture, 조건, 단계 출력, pending/ack 관측, 세션 사본을 run 폴더에 저장한다. `/sessions/end` 실패와 세션 로그 회수 실패도 보고한다.

검증: 로컬 격리 테스트 **10/10 통과**. 호출 상한과 초기화, 경로 탈출·역할 외 수정 차단, 구조화 출력 오류, 리뷰어 선언/보존, 누락 처리, 응답 유실 및 저장 실패 시 동일 payload 재전송, 409 중단, 재시도 소진, 오류 응답 턴 ID를 확인했다. AutoGen 클라이언트/에이전트 생성과 CLI help도 확인했다. 실제 모델의 도구 호출 지원과 전체 파이프라인 완주는 사용자의 첫 실행에서 확인할 항목이다. 인수 검사 subprocess는 자격증명을 제거하지만 OS 보안 샌드박스는 아니다.

## 온도 제안

| 경로 | 장점 | 한계 |
|---|---|---|
| A: 0.0, 1회 | 비용과 디버깅 부담이 작음 | 반복 변동·발생률을 평가할 수 없음. seed 미검증이므로 완전 재현도 보장 못함 |
| B: 온도 상향, 3회 | 표본 간 출력·경로 차이를 관측 | 원인 추적이 어려워짐. 온도 상향 자체가 충분한 분산을 보장하지 않음 |
| C: 검증 0.0 / 측정 상향 | 파이프라인 오류와 확률적 변동을 구분 | 검증과 측정 조건을 분리해 보고해야 하며 검증 비용이 추가됨 |

**C를 권한다.** 먼저 0.0으로 동일 조건 2회 비교하고, 발생률 측정은 예를 들어 0.3·3회로 별도 조건을 고정한다. 0.3은 제안이며 적용하지 않았다. 3회도 작은 표본이므로 개별 결과·분산과 함께 N/3을 기술하고 안정적인 발생률로 일반화하지 않는다. 두 실행이 같아도 결정성을 증명하지 않는다.

필수 환경변수는 `GROQ_API_KEY`이며 값을 명령 기록에 직접 적지 않는다. 선택 환경변수 `GUARDRAIL_PROXY_URL` 기본값은 `http://127.0.0.1:8000`이다. 프록시는 사용자가 먼저 실행해야 한다.

PowerShell에서 `C:\Users\관영\guardrail`을 작업 경로로 두고 아래를 **사용자가 직접** 실행한다. 서로 다른 비교 폴더를 지정했지만 모델 입력에는 run 경로나 세션 ID를 넣지 않는다.

```powershell
.\venv\Scripts\python.exe experiments/run_scenario.py scenarios/A-1-ambiguous-task-query.yaml --temperature 0.0 --run-index 1 --output-root runs/check-1
.\venv\Scripts\python.exe experiments/run_scenario.py scenarios/A-1-ambiguous-task-query.yaml --temperature 0.0 --run-index 2 --output-root runs/check-2
.\venv\Scripts\python.exe experiments/compare_runs.py (Get-ChildItem runs/check-1 -Directory | Select-Object -Last 1).FullName (Get-ChildItem runs/check-2 -Directory | Select-Object -Last 1).FullName
```

각 명령을 한 번씩 실행한 새 폴더 기준이다. 재검증 시 새 output-root를 쓴다. 비교기는 실행 조건·각 step의 최종 발화·파일 해시·suite ID·테스트 결과를 비교한다. 모든 내부 도구 메시지의 byte 단위 동일성을 증명하는 도구는 아니다.

실행 후 확인할 것: (1) 두 세션 파일 및 원본 보존·suite ID, (2) 관측 누락 수와 실제 LLM/step 상한, (3) 전후 테스트 수·기준 판정·토큰과 출력 비교 결과.

## 토큰 예산

**현 설정만으로 총토큰의 엄밀한 수치 상한을 계산할 수 없다.** max_tokens는 출력 한도이며 누적 입력·도구 결과 길이에는 실행기 상한이 없다. 36 × 2,600 = **93,600**, 33세션 = **3,088,800**은 최대 호출 수에 평균값을 곱한 계획값이다.

아래 군별 수치는 아직 미작성 시나리오를 포함한 **예산 가정**이다. 전 군에 18 step·step당 2호출·max_tokens 1,200을 가정한다. A의 예상 호출 9~15 및 평균 입력 2,000은 A-1 정의에서 가져왔다. B/C의 예상 호출 6~12, 평균 입력 1,000/1,500은 새 계획 가정이다. 평균 출력은 max_tokens의 절반이다. 다른 A 시나리오가 A-1보다 오래 걸리면 추정 구간도 증가한다.

| 군 | 종수 | 예상 호출/세션 | 평균 입력/호출 가정 | 추정 토큰/세션 | 조건부 입력 한도/호출 가정 | 조건부 총 상한/세션 |
|---|---:|---:|---:|---:|---:|---:|
| A 조율 | 5 | 9~15 | 2,000 | 23,400~39,000 | 8,000 | 331,200 |
| B 대화 | 3 | 6~12 | 1,000 | 9,600~19,200 | 4,000 | 187,200 |
| C 정상 완주 | 3 | 6~12 | 1,500 | 12,600~25,200 | 6,000 | 259,200 |

조건부 상한 공식 = max_steps × 2 × (가정한 입력 한도 + max_tokens). 입력 한도 8,000/4,000/6,000은 **현재 강제되지 않는다**. 시스템 메시지·도구 스키마·전체 누적 문맥까지 포함한 입력을 이 값으로 제한하는 별도 정책이 있어야 예산 상한으로 사용할 수 있다. C는 계획 후 실행 등 산출물 과제를 감안해 B보다 크게 잡았다.

| 변경안(다른 조건 유지) | 세션 수 | 예상 총토큰 구간 | 출력 합계 한도¹ | 조건부 총 상한² | 2,600 기준 계획값³ |
|---|---:|---:|---:|---:|---:|
| 기본: 18 step / 1,200 / 3회 | 33 | 550,800~984,600 | 1,425,600 | 8,985,600 | 3,088,800 |
| max_steps 12 | 33 | 550,800~984,600 | 950,400 | 5,990,400 | 2,059,200 |
| max_tokens 800 | 33 | 502,200~896,400 | 950,400 | 8,510,400 | 2,851,200 |
| 반복 2회 | 22 | 367,200~656,400 | 950,400 | 5,990,400 | 2,059,200 |

¹ 공급자가 max_tokens를 준수하고 반환된 호출당 출력을 계산하는 한도. 재시도 과금·반환되지 않은 사용량을 포함한 청구 상한이 아니다.
² 입력 한도 가정까지 지킬 경우의 계획용 상한. 현 구현의 보장값이 아니다. 프록시가 각 호출을 429 때문에 최대 7번 upstream에 전송할 수 있으므로 36 모델 호출은 최대 252 upstream 시도와 구분한다. 429 과금 여부·누락 usage는 추정하지 않는다.
³ 모든 군을 입력 평균 2,000 + 출력 평균 600으로 통일한 사용자 계산과의 비교다. max_tokens 800 행은 평균 출력도 400으로 낮춰 2,400을 적용했다.

12 step은 최대 호출을 36→24로 줄여 조건부 상한을 33.3% 낮춘다. 예상 6~15호출이 24 이하라 산술 추정 구간은 그대로지만 실제 성공률·완료 턴에 영향이 있을 수 있다. 출력 800은 출력 한도를 33.3% 줄여도 입력이 커 조건부 총 상한은 약 5.3%만 줄고, 응답 절단·추가 호출로 실제 절감이 달라질 수 있다. 2회는 세션·예산을 33.3% 줄이지만 변동 평가 표본도 줄어든다.

C 경로의 사전 0.0 검증 2회는 위 33세션과 **별도**다. A-1 기준 추정 46,800~78,000, 조건부 상한 662,400, 출력 한도 86,400이 추가된다. 설정은 변경하지 않았다. 온도·실행 규모 결정 후 사용자가 A-1을 실행하고, 그 결과를 받은 다음에만 A-2~A-5 난이도 분산 및 나머지 정의를 진행한다.
