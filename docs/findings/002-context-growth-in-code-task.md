## 입력 증가 분해

buffer_count=12는 각 에이전트의 최근 메시지 수를 제한한다. 시스템과 도구 스키마는 별도로 붙고 메시지 한 건의 길이는 제한하지 않는다. 매 step acceptance의 16개 테스트 상태 전체와 recent_messages를 전달하며 과거 묶음도 버퍼에 남는다. read_file은 파일 전체를 반환한다. 최종 strict 호출은 남은 assistant/tool 이력을 observed_records JSON으로 다시 직렬화한다. 따라서 버퍼가 차기 전 상승하고 이후 길이가 다른 기록이 교체되며 출렁인다.

같은 developer의 첫 호출끼리 비교한 분해다. 값은 실제 본문의 문자 수이며 토큰이 아니다. system/tool content는 원문 길이, JSON 하위 값·도구 스키마·assistant 메시지는 ensure_ascii=False JSON 직렬화 길이다. 키·구분자/메시지 포장 오버헤드 일부를 제외하므로 합을 provider prompt_tokens로 해석하지 않는다. 하위 요소별 실제 토큰은 제공자 로그에 없어 측정 불가다.

buffer6 추정은 usage가 있는 작업 요청 27건에서 시스템을 유지하고 최근 6개 메시지만 남긴 뒤, 첫 메시지가 tool 결과면 제거했다. 현재 데이터는 호출당 도구가 최대 1개여서 이 뷰 변환에 다중 도구 묶음 문제가 없다. 각 요청의 알려진 prompt_tokens × (변환 본문 문자 수 / 원본 본문 문자 수)로 계산했다. 작업 요청 입력은 99,142 → 약 65,481. 최종 strict 요청과 출력은 원래 값으로 고정했다. 최종 요청에는 원래 이력이 필터링·재직렬화돼 있어 전체 buffer6 요청을 정확히 복원한 계산이 아니다. 문자/토큰 비율, 앞으로 생성될 도구·파일·응답 변화, 오류 소비도 알 수 없다. 실제 buffer6 소비와 성능은 별도 실행해야 측정된다. 이 수치를 보장 상한이나 절약률로 쓰지 않는다.
