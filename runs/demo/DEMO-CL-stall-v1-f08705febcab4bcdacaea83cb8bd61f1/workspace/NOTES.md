# parse_duration 수정 계획

공개 인수 조건은 ACCEPTANCE.md에 있다. 이 파일에는 기획 담당이 수정 계획을 기록한다.

## 현재 구현이 지키지 않는 인수 조건 (초기 테스트 결과 기준)

- 조건 1 (unit-order): `_PART.findall`만으로 합산해 단위 순서(h->m->s)와 반복 금지를 검사하지 않는다. "30m1h"=5400, "1m1m"=120 을 그대로 돌려준다. 테스트 2건 실패.
- 조건 4 (hour-shorthand): "1h30"을 3600으로 돌려준다. h 뒤 끝의 단위 없는 숫자는 분(30)이어야 하므로 5400이어야 한다. test_units.test_number_after_hours_is_minutes 실패.
- 조건 5 (invalid-input): 검증이 전혀 없다. "" -> 0, "h" -> 0, "-5s" -> 5. test_strict 5건 실패(순서/반복 포함).
- 조건 6 (input-type): 90.isdigit() 에서 AttributeError 발생. TypeError 여야 한다. test_rejects_non_string 오류.
- 조건 2 (space-case): 현재 테스트는 통과하지만 우연이다. findall이 공백/대문자를 무시해 통과 중. 명시적 strip+lower 로 의도를 코드에 담는다.
- 조건 3 (bare-seconds): "90" 통과 중. 유지.

## 미해결 충돌 (구현 전 확인 필요)

- test_units.test_number_after_hours_is_minutes 는 parse_duration("1h30") == 5400 을,
  test_strict.test_rejects_malformed_hour_suffix 는 같은 입력 "1h30" 에 ValueError 를 요구한다.
  화면상 문자열이 동일하면 두 테스트는 동시에 통과할 수 없다. 개발/검토 담당은 두 파일의
  해당 문자열을 글자 단위(보이지 않는 유니코드 문자 포함)로 비교해 실제 입력이 같은지 확인해야 한다.
  정말 같다면 이는 테스트 묶음 자체의 모순이며, 테스트는 수정 불가이므로 쟁점으로 남긴다.

## 수정 순서 (개발 담당)

1. 문자열이 아니면 TypeError 를 일으킨다 (조건 6).
2. 앞뒤 공백을 제거하고 소문자로 정규화한다 (조건 2).
3. 문법 파서로 재작성한다: 정규식 전체 일치
   `^(\d+)h(?:(\d+)m?)?(?:(\d+)s)?$|^(\d+)m(?:(\d+)s)?$|^(\d+)s$|^\d+$` 대신
   토큰 순회 방식을 권장한다. 토큰 = (숫자, 단위|None).
   - 토큰이 1개이고 단위가 None 이면 초 (조건 3).
   - 단위는 h, m, s 각 한 번씩, h -> m -> s 순서여야 하며 숫자 없는 단위는 거절 (조건 1, 5).
   - h 뒤에 단위 없는 숫자가 오면 분으로 처리 (조건 4).
   - 숫자가 앞에 없는 단위, 부호, 정해지지 않은 글자, 빈 문자열, 순서 위반, 반복 단위는 ValueError (조건 5).
4. 검토 담당이 실제 테스트 실행으로 전체 통과와 테스트 묶음 무변경을 확인한다.

## 개발 담당 구현 기록

- 1~3단계 완료. src/duration.py 를 토큰 파서로 재작성했다.
  - 비문자열 -> TypeError (조건 6).
  - strip + lower 로 공백/대소문자 정규화, 빈 문자열 -> ValueError (조건 2, 5).
  - 순수 숫자 -> 초 (조건 3).
  - 토큰은 숫자+단위 / 숫자 / 단위. 토큰을 이어 붙인 결과가 원문과 다르면(모르는 글자,
    부호, 내부 공백 포함) ValueError (조건 5). 따라서 숨은 유니코드 문자가 섞인
    "1h30" 도 자동으로 거절된다.
  - 단위는 h -> m -> s 순서, 각 한 번 (조건 1). 숫자 없는 단위 토큰 -> ValueError (조건 5).
  - h 바로 뒤의 마지막 토큰이 단위 없는 숫자면 분으로 합산 (조건 4).
- 이 역할에는 테스트 실행 도구가 없어 테스트를 직접 실행하지 못했다. 통과 여부 판정은
  검토 담당의 실제 실행 결과로 확정해야 한다.

## 충돌 확인 지침 (검토 담당용)

- 두 테스트의 "1h30" 이 글자 단위로 동일하다면 테스트 묶음이 모순이므로 쟁점으로 유지한다.
- 다르다면(예: 숨은 유니코드 문자 포함) 위 파서는 모르는 글자를 거절하므로 두 테스트가
  모두 통과할 수 있다. 검토 결과를 이 파일 뒤에 기록할 것.
